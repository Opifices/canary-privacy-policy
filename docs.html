Canary User Guide & Documentation

On-demand regression checks for Jira Automation: verify the outcome, not just the run.

1. Overview

Jira Automation audit logs tell you whether a rule triggered and ran. They cannot tell you whether the rule still produces the business outcome you expect after someone edits it.

Empirical finding: In our automated experiments, modifying a rule's action led Jira's audit log to report SUCCESS, even though the expected label was no longer added. Canary detected this silent regression immediately as FAIL.

Canary is an on-demand regression check application built natively on Atlassian Forge. You select a target test project, the stimulus trigger label, and the expected output label, then click Run Canary check.

2. How It Works: Stimulus and Control

Instead of creating random test tickets, Canary creates a simultaneous pair of issues in your Jira project:

  • Stimulus Issue: Carries your trigger label (e.g. cny-test), so your automation rule should evaluate its condition and act on it.
  • Control Issue: Identical in all respects, but deliberately created without the trigger label, so your automation rule must leave it untouched.

Canary monitors both issues over an exact 25.0-second observation window using Jira's native issue changelogs and server timestamps, computing a deterministic verdict.

3. Verdicts Explained

  • PASS The rule worked as intended. The stimulus issue received the expected label within 25 seconds, and the control issue remained completely clean for the entire observation window.
  • FAIL The expected outcome did not occur. The expected label was never added to the stimulus issue within 25 seconds (or was delayed beyond the SLA).
  • OVERREACH Your rule is affecting unrelated work! The control issue also received the action label, indicating that the rule's condition is too loose.
  • INCONCLUSIVE Transient read or permission issue. Canary could not read the full changelog or Jira API returned an error. A read error is never reported as FAIL.
  • INVALID Contaminated initial state. The test inputs already carried the expected label at creation time.

4. Setup & Best Practices

  • Use a dedicated test project: Canary creates real, permanent Jira issues. Automation rules, webhooks, and notifications in that project can react to them.
  • Supported project types: Software and Business (Jira Work Management) projects are fully supported. Jira Service Management (JSM) projects are excluded.
  • Finding test issues: Search with JQL: summary ~ "CANARY" AND summary ~ "TEST".
  • Permissions: Checks run with user permissions (asUser). The user needs Administer projects and Create issues in the target project.

5. Atlassian Rovo & MCP Integration (Preview)

Canary exposes two tools through Atlassian Forge's rovo:mcp infrastructure:

  • Run Canary Check (canary-run-check): Creates a stimulus and control pair in a project previously configured from the Canary UI. Protected by an atomic KVS rate-limiting lock (maximum 1 check per project per minute).
  • Get Canary Recent Results (canary-get-recent-results): Purely read-only tool that queries the latest evaluated verdicts for accessible Jira projects.
